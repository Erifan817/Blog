# 把"判断"从语言里拆出来：用 Jev 做一套校准路由架构

## 一、背景：Jev 与 System One 模型

Jev 是 TypeSafe AI 于 2026 年 9 月 15 日发布的第一个 **System One 模型**。创始人 Diogo Almeida 出身 OpenAI，是 InstructGPT 论文的主要作者之一，也参与建立了后来被广泛采用的 RLHF 训练流程。

Jev 的特点是：把大模型最引以为傲的能力——生成文字——整个砍掉，只保留"判断"。官方口号是 *"Decisions, not strings"*（要决策，不要文本）。

"System One"这个名字借自心理学家卡尼曼的《思考，快与慢》：System 1 是快直觉，System 2 是慢思考。TypeSafe 的判断是，今天的 LLM 都在被当 System 2 用——而一个系统里大量高频、琐碎的判断，本该由 System 1 的反射来完成。Jev 补的就是这个位置。

| 维度 | 传统大模型 | Jev |
|---|---|---|
| 输出 | 自由文本（还需解析、校验、防幻觉） | 三种类型化原语：**Choice（选择）/ Score（评分）/ Noul（布尔概率）**，结构提前定义 |
| 生成方式 | 自回归，一个 token 一个 token 蹦 | 并行采样，所有判断一次算完（最多 255 个选项） |
| 端到端延迟 | 3 秒 ~ 329 秒 | 70 ~ 500 毫秒（厂商称特定工作流最高快 193.6 倍） |
| 定价 | 输出通常比输入贵数倍 | 输入 $0.042/百万 token，**输出免费**（厂商称综合成本最高省 444.6 倍） |
| 训练方法 | RLHF / RLVR | **RLCD**（Reinforcement Learning for Calibrated Decisions）：模型报告 80% 置信度，实测就该约 80% 正确 |

性能数字全部来自厂商自述——参考链接在文末，我的保留态度写在最后的免责声明里。但架构方向本身值得讨论：它第一次把"判断"从"语言"里剥离出来，单独定价、单独部署。

如果真有一个又便宜、又快、还会诚实报告把握的判断器，它应该被放在系统的哪些位置？

我想到三个：

- **请求入口**：决定一个请求交给哪个模型——一次调用花 1 美分还是 1 美元，差距就在这一步；
- **歧义升级点**：Agent 想把问题抛给人的那一刻，先判断这个问题是不是真的需要人；
- **任务分派层**：多 Agent 系统里，活分给谁、结果算不算数，都由它定。

下文的三层设计，就按这个顺序展开。

## 二、两个真实的疼点

### 疼点 1：全用旗舰模型，等于烧钱干杂活

真实的业务流量里，通常七成以上是简单请求：分类、打分、路由、抽取、判断"要不要继续"。全用旗舰 LLM 处理，就像让主任医师给每个病人量体温。模型级联（Model Cascading）不是新想法——FrugalGPT 在 2023 年就论证过"小模型先行、大模型兜底"的经济学——但这个模式一直有一个没解决好的软肋：

**路由器自己的判断不可信。**

用传统 LLM 当路由器，它经常"不知道自己不知道"：自信满满地把难题错派给小模型，用户拿到一个流畅的错误答案。省钱省出来的全是事故。这就是为什么过去级联方案里，路由器阈值只能设得极保守，省钱效果大打折扣。

### 疼点 2：Agent 动不动就"问人"

Astra 发布后，开发者抱怨最多的不是能力，而是行为：它被设计成"遇到歧义先问清楚而不是自行假设"，结果频繁暂停工作流，反而没大家想的那么自主。

问题不在于"问"，而在于它把所有不确定性都路由给了同一个出口：人类。人被打断一次的代价很高，Agent 决定要不要打断时却草率得很——这大概是当下人机协作里最拧巴的资源错配。

## 三、第一层设计：Jev 当前置路由器

```
          ┌──────────────────────────────────────────────┐
          │                请求 / Agent 任务                │
          └──────────────────────┬───────────────────────┘
                                 ▼
                   ┌──────────────────────────┐
                   │   Jev 路由：分类 + 打分    │
                   │   70ms · 近零成本 · 带置信度 │
                   └──────────────────────────┘
            ┌─────────────────────┼─────────────────────┐
            ▼                     ▼                     ▼
     简单结构化判断           中等复杂度              低置信 / 复杂
    （置信度 ≥ 95%）              │                      │
            │                     ▼                      ▼
            ▼               Flash 小模型            旗舰 LLM
     Jev 直接出结果         （便宜、快）           （贵、慢，但值）
            │                     │                      │
            └─────────────────────┴──────────────────────┘
                                  ▼
                       结果 + 全链路审计日志
```

省钱的数学很简单：七成流量被拦在便宜通道里，只有真正难的 30% 才配得上旗舰模型。但这个设计要成立，先得解决第二节说的那个软肋——

**校准让阈值第一次变得有意义。**

传统 LLM 说"我有 95% 把握"，和它真实的正确率没有稳定关系；而 RLCD 训练的 Jev，报告的置信度被直接对齐到实测正确率。这意味着"置信度 ≥ 95% 自动放行、80–95% 用小模型加抽检、< 80% 升级旗舰"这样的规则，才从拍脑袋变成了工程。

再加 70ms 延迟和近零成本，路由这一步就不再拖后腿——前置路由免费了，级联才真正划算。这是它相对"用大模型当路由器"的真实增量。

## 四、第二层设计：给"问人"装一个分类器

这是本文真正想说的部分。

**Agent 说"我需要问人"时，绝大多数时候是撒谎了。** 那些停顿背后是四种完全不同的问题，只有两种真正需要人：

| 歧义的真实身份 | 本质 | 正确的去处 | 例子 |
|---|---|---|---|
| **信息缺口** | 数据不在上下文里 | 工具调用去查，**不该问人** | "这个用户的订单状态？" → 查数据库 |
| **能力缺口** | 模型想不明白 | 升级更强的 LLM / 多花算力推理 | 复杂推理卡壳 → 换旗舰模型重跑 |
| **偏好/价值缺口** | 只有组织里的人知道答案 | **真·问人** | "这条退款规则，公司到底想不想放宽？" |
| **不可逆/高风险** | 后果无法撤销、超出授权范围 | **强制问人**，与置信度无关 | 删库、打款、对外发函 |

现在的 Agent 问人，大部分是在拿人类的脑子当"查表工具"（信息缺口）或"算力外挂"（能力缺口）——这两种都应该被自动化消化。真正值得打断人的，只剩目标、偏好、责任这三样机器没有的东西。

于是架构里多出一个组件：歧义分类器。分工是——

> **LLM 负责发现歧义，Jev 负责给歧义分类。**

发现"这里含糊"需要语言理解，判断难；但"这个含糊属于哪一类"是典型的分类任务，正好是 Jev 的主场。发现难题归大模型，分类难题归小模型，各司其职。

配套两个细节，让人被打断得更体面：

**1. 问人也要"问得像样"。** 轮到真问人时，输出不该是一段开放散文，而应该是一张类型化决策卡：选项 A/B/C + 各自校准概率 + 后果一句话。让人做选择题，而不是问答题——把人的注意力当成最贵的 API 来省着用。

**2. 攒着问，别逐条问。** 判定"需要人"之后先入队，凑一批一次性给出。一次打断解决五个问题，永远好过五次打断各解决一个。

## 五、第三层设计：多 Agent 编排——同一个模式，再长一层

前置路由和歧义分类都不是终点。同一个模式往上再长一层，就是多 Agent 编排：路由的对象从"选哪个模型"变成"派给哪个子 Agent"。

编排者的工作流长这样：

```
                   ┌──────────────────────────┐
      问题 ──────▶│  Jev 分类：这是哪一类任务？  │
                   └────────────┬─────────────┘
          ┌─────────────┬──────┴──────┬─────────────┐
          ▼             ▼             ▼             ▼
     研究 Agent     代码 Agent     数据 Agent     写作 Agent
          │             │             │             │
          └─────────────┴──────┬──────┴─────────────┘
                               ▼
                   ┌──────────────────────────┐
                   │  Jev 验收：Score 打分      │
                   │  低分 → 打回重做 / 升级     │
                   └────────────┬─────────────┘
                               ▼
                           归并输出
```

几个要点：

**1. 分派是分类任务，验收也是。** "这个问题该给谁"和"这个结果能不能用"，都是典型的结构化判断——偏偏是编排者最不该动用旗舰模型亲自干的活。编排者保持轻，专业子 Agent 保持窄，Jev 在两头当质检。

**2. 独立子任务并行分派。** 研究类问题天然可拆：并行发出去，各自带预算和时限，回来归并。Jev 的 Score 原语正好可以当"归并前的质检关卡"——低分的不合并，打回重做，或者升级给更强的模型。

**3. 子 Agent 也有"上报时刻"。** 子 Agent 卡住时向编排者上报，编排者面对的还是那套熟悉的分类逻辑：加资源重跑 / 换个专门的子 Agent / 亲自下场 / 升级给人。递归的是同一个模式：分类 → 分派 → 验收 → 升级。

**4. 延迟会在层间叠加。** 单看 70ms 很快，但如果请求路径上串了四五道前置判断，每道 70ms 加起来就成了用户可感知的卡顿。层数要克制，能并行的判断尽量并行。

这里有个我觉得最有意思的观察：**这是一个分形架构（fractal architecture）**。请求级选模型、任务级选子 Agent、结果级决定合并还是打回、歧义级决定问人还是升级——每一层长的都是同一张脸：分类 → 分派 → 验收 → 升级，区别只是粒度。而每一层的那台"分类器"，都应该又便宜、又快、又校准。

## 六、两条不能混的线：校准管省钱，硬规则管保命

整个系统里最容易犯的错误，是把两类决策塞进同一个机制。它们必须分开：

- **概率线**：信息缺口、能力缺口的分类，用校准置信度驱动，允许阈值调优，错了也就是多花点钱或多绕一步。
- **硬规则线**：不可逆、越权、涉资金、涉安全的动作，不走概率判断，直接写死升级。Jev 说置信度 99% 也没用——因为校准的 99% 意味着每 100 次还会错 1 次，而不可逆动作错 1 次就是灾难。

错误成本在这里高度不对称：把简单任务错升级给旗舰模型，代价是钱；把"真该问人的"错判给自动化，代价是系统在错误假设上规模化狂奔。**所以路由器的第一美德不是聪明，是不装懂。**

## 七、具体实施方案

设计讲完了，这一节给一条可落地的路径。先交代前提：Jev 目前处于早期访问阶段，下面按"有 Jev"设计；如果你现在就想动手，替代方案是用小参数模型 + 结构化输出（JSON Schema 约束解码）+ 温度 0，再拿自己业务的标注数据做一次**置信度校准**——让"报告 80%"对齐"实测 80%"。校准这一步不可省，它是整个架构的地基。

### 7.1 组件清单

| 组件 | 职责 | 实现要点 |
|---|---|---|
| 前置路由 | 请求分类 + 置信度输出 | 无状态、可横向扩；Jev Choice 原语 |
| 路由执行层 | 三级瀑布的实际执行 | 每级独立超时/重试/熔断；L1 直答、L2 Flash、L3 旗舰 |
| 歧义分类器 | 拦截 Agent 的"问人"，先分类 | 挂在 Agent 循环内：LLM 发现歧义 → Jev 分类 |
| 决策卡生成器 | 把"问人"变成选择题 | 选项 + 校准概率 + 后果一句话；攒批队列、去重 |
| 硬规则闸 | 不可逆动作强制升级 | 纯规则表，不走任何概率判断 |
| 审计与抽检 | 日志四元组 + 校准漂移监控 | 定期抽样旗舰复核；错误率超阈值触发重校准 |

### 7.2 核心路由（伪代码，接口以 Jev 实际 API 为准）

```python
route = jev.choice(
    state=compose(request.text, session.context),
    options=["SIMPLE_STRUCTURED", "MEDIUM", "COMPLEX"],
)

match route.value:
    case "SIMPLE_STRUCTURED" if route.confidence >= 0.95:
        return jev_answer(request)      # L1：路由器直接出结构化结果
    case "SIMPLE_STRUCTURED" | "MEDIUM" if route.confidence >= 0.80:
        return flash_llm(request)       # L2：小模型，便宜快速
    case _:
        return frontier_llm(request)    # L3：旗舰兜底（复杂任务，或置信度不够）
```

### 7.3 歧义分类（伪代码）

```python
# LLM 负责发现歧义，Jev 只负责分类
amb = agent.detect_ambiguity(task)
kind = jev.choice(
    state=amb.context,
    options=["INFO_GAP", "CAPABILITY_GAP", "VALUE_GAP", "IRREVERSIBLE"],
)

match kind.value:
    case "INFO_GAP":       return run_tool(amb.missing)         # 信息缺口：自己查
    case "CAPABILITY_GAP": return retry(stronger_model, task)    # 能力缺口：升级重跑
    case "VALUE_GAP":      decision_queue.push(amb)              # 价值缺口：攒批问人
    case "IRREVERSIBLE":   return human_gate(amb, force=True)    # 硬规则：无条件升级
```

### 7.4 分阶段上线：影子模式先行

| 阶段 | 时间 | 做什么 | 退出条件 |
|---|---|---|---|
| **Phase 0 影子** | 第 1-2 周 | Jev 只记录不执行，全流量照走旧路径；离线对比它的路由决策与真实结果 | 校准误差 ≤ 5% |
| **Phase 1 小流量** | 第 3-6 周 | 只放行"简单结构化 + 置信 ≥ 95%"的白名单场景 | 线上错误率 ≤ 基线 |
| **Phase 2 分类** | 第 2 个月 | 接入歧义分类器，替换 Agent 的"直接问人" | 人工打断率下降，且无漏判事故 |
| **Phase 3 编排** | 第 3 个月 | 多 Agent 分派 + Score 验收回传 | 单任务成本下降 ≥ 50% |

Phase 0 要多说一句：影子模式是整个方案的信任来源。厂商数字再漂亮，也要拿你自己的流量重新证明一遍——影子期顺便就完成了开头说的置信度校准。跳过这一步直接上生产，等于把架构押在别人的一份报告上。

## 八、防坑清单（写给未来要实现这套东西的自己）

1. **分布漂移**。上线三个月后用户的问题类型会变，路由准确率悄悄下滑。要做持续抽检：定期从"Jev 判为简单"的流量里抽样，交给旗舰模型复核；错误率抬头就触发重新校准。
2. **审计链**。每个决策记录四元组：谁判的、置信度多少、走了哪条通道、最终结果。出了问题能分清是路由器看走眼，还是执行者做错了。
3. **语义歧义的边界**。"用户这句话到底想表达什么"这种开放式理解，本身可能就需要语言能力——别让 Jev 越界去干 LLM 的活。分类器分的是"歧义的类型"，不是"歧义的语义"。
4. **别迷信厂商数字**。193.6 倍加速、444.6 倍省钱都是 TypeSafe 自己的报告。真实流量下的准确率、校准质量、边界行为，要用自己的数据重测。

## 九、更深一层：注意力经济学

把前面几层连起来，分工其实很整齐：Jev → Flash → 旗舰 LLM，是按任务难度分配算力；工具自查 → 模型升级 → 人类决断，是按歧义类型分配注意力；再垫一层风险硬闸，不可逆动作无条件升级，与置信度解耦。

这套东西回应的是一个我越来越相信的判断：AI 不会整体取代人，而是把人挤到两端——定义问题和验收结果。但"怎么退"一直没有机制。我的答案是：

> **把人的注意力从"能力补充"里解放出来，只留给"价值判断"。**

人的每次被打断，都应该值回打断价。机器能自己查的别麻烦人，机器能自己想的别麻烦人，机器想了还想不明白的再升级模型，模型升级也填不满的——那才是"人"的位置。那个位置剩下的东西，正是目标、偏好、责任：机器没有，也不该有。

## 十、免责声明

- 本文所有关于 Jev 的性能数字（193.6x、444.6x、70ms、输出免费等）均来自 TypeSafe AI 的发布材料与媒体报道，独立基准尚未出现。创始人自己在发布公告里也写了："Extraordinary claims require extraordinary evidence."
- "无幻觉"的说法要打折扣：Jev 不会生成编造的文本，但类型正确的错误决策照样存在——答案错了但格式完美，反而更隐蔽。
